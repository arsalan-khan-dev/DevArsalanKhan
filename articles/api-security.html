The API Is the Attack Surface

Why legitimate requests can still become a breach

Nobody breaks into your application anymore. They just ask it politely for data, and it says yes.

Here's something that should bother you more than it probably does. When T-Mobile disclosed in January 2023 that a hacker had pulled personal data from roughly 37 million customer accounts, there was no phishing email involved. No stolen password. No malware on an employee laptop. The attacker found a single API, started calling it in late November 2022, and kept calling it for six weeks before anyone noticed. T-Mobile's own filing described the access method plainly: a bad actor obtained data through one API, and the API worked exactly as it was built to work. Nobody broke it. They just used it more than anyone expected an outsider to.

That distinction is the whole subject of this article. Most of the security conversation over the last decade trained developers to think about attacks as intrusions, as someone forcing their way past a control that was supposed to stop them. APIs quietly changed the shape of the problem. The control often isn't missing. It's just answering a question nobody thought to ask: what happens when a legitimate credential is used exactly the way it was designed to be used, ten thousand times, against every account in the database instead of one?

I've spent enough time reading API traffic logs to have an opinion on this, and it's an uncomfortable one. The API layer is where most modern breaches actually originate, and it's the layer most engineering teams understand least. Not because APIs are exotic. Because they sit precisely at the point where architecture decisions, business logic, and authorization checks are supposed to meet, and that intersection is exactly where things get skipped under deadline pressure.

This isn't a piece about SQL injection or about phones. I've written about device-level compromise elsewhere. This is about the layer that increasingly sits behind almost everything: the mobile app, the web frontend, the partner integration, the internal microservice mesh. If you build software today, you are, whether you frame it this way or not, primarily building and shipping APIs. Everything else is just a client.

Every App Is Just a Frontend for an API You Forgot to Secure

Start with a pattern I see constantly during assessments. A team builds a mobile app and a web app for the same product. Both need to talk to the backend, so someone builds a REST or GraphQL API that both clients consume. That's sound architecture, and nobody would flag it in a design review.

The problem shows up in how the team then reasons about trust. The web app has a login screen, so naturally there's authentication logic wired up carefully there. The mobile app has the same login screen, mirrored. But the API underneath, the thing actually holding the data, often gets treated as an implementation detail. It's "internal." It's "just for our apps." Nobody else is supposed to be calling it.

That assumption is false the moment the API is reachable from the public internet, which it almost always is, because your mobile app has to reach it from cellular networks, coffee shop Wi-Fi, and airport lounges around the world. An API reachable by your app is reachable by anyone with a proxy tool and twenty minutes of patience. Burp Suite or a similar intercepting proxy sits between the app and the API, and every request the app makes becomes visible, editable, and replayable. The client-side code that "enforces" business rules in the mobile app enforces nothing at the API layer. It's a UI convenience, not a security boundary.

Security theater at the client and a wide-open door at the server is a more common architecture than most engineering leaders want to admit.

I want to be precise about why this happens, because it isn't laziness. It's a reasonable-sounding assumption that turns out to be wrong under scrutiny. Developers build the mobile app first, or at the same time as the API, and they test the whole thing through the app's UI. The UI only lets you do certain things in a certain order, so testing through the UI only ever exercises the "happy path" through the API. Nobody manually crafts a request that skips a step, or substitutes another user's ID, because the app's interface doesn't offer that option. The vulnerability isn't invisible. It's just never tested, because the tool used to test it (the app itself) was specifically designed not to expose it.

This is the first mental shift that matters if you're building APIs seriously: the client is not a security control, it's a convenience layer, and every check that only exists in client code does not exist at all from a security standpoint.

The Vulnerability That Doesn't Look Like a Vulnerability

If you ask most developers to name a security flaw, they'll describe something that looks broken: unescaped input, a missing sanitization step, a library with a known CVE. Something with a visible defect.

The most damaging class of API vulnerability doesn't look broken at all. It looks like a perfectly functioning feature that happens to be missing one comparison.

This is broken object level authorization, usually abbreviated BOLA, and it has held the number one spot on the OWASP API Security Top 10 since the list's creation in 2019, and it kept that position when OWASP updated the list in 2023. It is represented in roughly 40 percent of all real-world API attacks. That is not a niche issue. That is the dominant failure mode in production APIs today.

The mechanics are almost embarrassingly simple. An endpoint like GET /api/invoices/8842 returns invoice 8842 to whoever is logged in and requests it. The API checks that you're authenticated. It checks that the token is valid. It does not check whether invoice 8842 actually belongs to you. Change the number in the URL to 8843, and if you're authenticated at all, you now have someone else's invoice. No exploit. No injection. Just a number, incremented.

I want to sit with why this keeps happening, because the reason says something true about how software actually gets built. Authentication and authorization get conflated constantly, even by experienced developers, because they feel like the same problem from inside a sprint. "Is this user allowed to see this?" gets answered with "is this a logged-in user?" and the second question is so much easier to implement that it quietly substitutes for the first. Authentication (who are you) is a solved problem with mature libraries. Authorization (what are you allowed to touch, specifically, on this specific object, right now) has to be re-derived for every single resource type in your system, and it doesn't come free from any framework. It has to be deliberately written, endpoint by endpoint, object by object.

That is expensive in a way that doesn't show up until it's tested properly, which is exactly why it's so often skipped under a deadline. Nothing about a BOLA vulnerability throws an error during normal development. The feature works. It works for the developer testing it with their own account, which is the only account they have. It works in the demo. It works in production, for the correct user, indefinitely, right up until someone changes a number in a request and it works for the wrong user too.

A vulnerability that never produces an error message is a vulnerability that never gets reported by the people who could have caught it.

The realistic developer question here isn't "how do I avoid BOLA in the abstract." It's: every single endpoint that accepts an object identifier, whether that's an invoice number, a user ID, an order ID, a document ID, needs an explicit server-side check that the authenticated principal actually owns or has been granted access to that specific object. Not that the principal is logged in. Not that the object exists. That this specific relationship holds, checked fresh, on every request, regardless of what the client claims or what the UI would normally allow.

This has to happen at the API layer, every time, with no exceptions carved out for "trusted" internal calls, because internal callers get compromised too, and because today's internal-only endpoint is next quarter's partner integration.

Where Authentication Quietly Becomes a Liability

The second most common category on the OWASP list is broken authentication, and it deserves more nuance than "use strong passwords," because the actual failures at the API layer are rarely about password strength. They're about how tokens are issued, how long they live, and what an attacker can do with one once they have it.

A meaningful share of API compromises don't involve stealing a password at all. They involve stealing or forging a token, because once you have a valid session token, the API generally doesn't ask who you are again. It trusts the token. That trust is the entire security model, and it's only as strong as how carefully the token was issued, how long it remains valid, and how easily it can be intercepted or replayed.

A few patterns show up over and over in real assessments:

Long-lived tokens with no meaningful expiry. A JWT that's valid for thirty days is convenient for the user, who doesn't have to log in constantly. It's also a thirty-day window for an attacker who intercepts it once.

Tokens that carry too much authority. A single token that grants full account access rather than a scoped set of permissions means a leak anywhere in the chain, a logging library that accidentally captures headers, a third-party analytics SDK, a misconfigured error reporting tool, hands over everything.

Password reset and account recovery flows that are weaker than the login flow itself. Attackers rarely brute-force a well-protected login form. They target the recovery flow, because it was built later, tested less, and often skips rate limiting that the main login path has.

Inconsistent enforcement across endpoints. MFA is enforced on the web login but not on the API endpoint the mobile app uses, because the mobile authentication flow was implemented separately and nobody unified the requirement.

That last one is worth dwelling on, because it's an architectural failure disguised as an implementation detail. When authentication logic is duplicated across a web login endpoint, a mobile login endpoint, and maybe a partner API login endpoint, each one is a separate opportunity to get it slightly wrong. Security engineers call this security drift: three implementations of the same conceptual control, built at different times by different people, that were identical on day one and have quietly diverged ever since.

The fix isn't complicated to describe, though it's genuinely hard to retrofit into a system that already has three login paths: authentication and token issuance should be a single, shared service that every client, web, mobile, or partner, calls through the same code path. Not three implementations that are supposed to behave the same way. One implementation, reused.

There's a deeper design mistake sitting underneath a lot of this, one worth naming directly: teams tend to treat a bearer token like a name rather than what it actually is, which is closer to cash. A bearer token, whether it's a JWT, an OAuth access token, or a simple opaque session identifier, grants access to whoever possesses it, full stop. The API generally has no way to verify that the entity presenting the token is the same entity it was originally issued to. A token that leaks, through a logging mistake, an overly permissive browser extension, a compromised third-party SDK, or plain interception on an unencrypted connection, is immediately usable by whoever now holds it, no questions asked.

That has a direct design implication most teams skip: the blast radius of a single leaked token should be as small as reasonably possible. Short expiry windows paired with a refresh mechanism beat long-lived tokens issued once and trusted for weeks. A token that expires in fifteen minutes and gets silently refreshed limits how long a leak stays useful. A token valid for thirty days because refresh logic felt like unnecessary complexity turns any single leak into a month-long exposure window. The same logic applies to scope: a token issued for a banking app's balance-check feature shouldn't, structurally, be capable of authorizing a funds transfer, even if the underlying account can do both. None of this is exotic. OAuth 2.0 was explicitly designed around scoped, short-lived tokens. The gap isn't knowledge. It's that scoped tokens take more upfront design work than one token that does everything, and the cost of that shortcut stays invisible until a token leaks somewhere nobody expected.

The Endpoints Nobody Remembers They Built

Authorization and authentication problems assume you know which endpoints exist. A lot of the risk in real production systems doesn't clear even that bar. There's a category of API risk that has nothing to do with how well any individual endpoint is written, and everything to do with how many endpoints exist that nobody currently tracks. OWASP calls this improper inventory management, and it's easy to dismiss as a housekeeping issue rather than a real vulnerability class. It isn't. An API you don't know about is an API you cannot patch, cannot monitor, and cannot include in a security review, because you don't know to look for it.

This shows up in a few recognizable forms. There's the v1 of an API that was supposed to be deprecated when v2 shipped, except the mobile app on older devices still calls v1, so it was never actually decommissioned, and it never received the authorization fix that v2 got six months later. There's the internal admin endpoint, spun up quickly for a support tool, that was never meant to be public but sits on the same domain and was never removed from the load balancer's routing rules. There's the staging environment API, deployed with looser security controls for testing convenience, that gets indexed by a search engine or discovered through a subdomain enumeration scan and turns out to be pointing at a copy of the production database.

None of these require a sophisticated attacker to find. Attackers routinely enumerate subdomains, brute-force common API path patterns (/api/v1, /api/internal, /api/admin, /api/debug), and scrape JavaScript bundles from web apps for hardcoded endpoint references, because frontend code frequently reveals the shape of a backend API even when the backend itself isn't documented anywhere public. A mobile app's decompiled code does the same thing even more directly, because mobile clients routinely embed full API base URLs and endpoint paths as string literals.

The API you forgot you built is often more dangerous than the one you're actively defending, because it's the one nobody is watching.

This is why API inventory has become its own discipline rather than an afterthought bolted onto a security review. Practically, that means maintaining a living registry of every API, every version, every environment, tied to an owner and a decommission date, and actually enforcing that decommission date rather than letting deprecated endpoints linger indefinitely because turning them off might break something nobody remembers depends on them. It also means recognizing that shadow APIs, ones deployed outside the normal review process because a team needed to move fast, are not an edge case. They are a predictable and recurring output of how software organizations actually operate under pressure.

When the Business Logic Is the Vulnerability

Somewhere around API3:2023 in the OWASP list, and more clearly in API6, the framework acknowledges something that doesn't fit neatly into a technical checklist: some of the most damaging API weaknesses aren't bugs in the conventional sense. The code does exactly what it was designed to do. The design itself is the problem.

Consider a discount code API. Enter a valid code, get a percentage off. Nothing wrong with the endpoint in isolation. Now consider what happens if that endpoint has no rate limit and no check on how many times a single account can apply different codes. An attacker scripts ten thousand attempts against a known code pattern in an afternoon, and what was a marketing feature becomes a fraud vector, not because any individual request violated a rule, but because the endpoint never asked whether this pattern of use made sense for a real customer.

The same shape of problem appears in flight booking systems that don't rate-limit seat reservation requests, in resale platforms where a "reserve item" API can be called repeatedly to lock inventory without ever completing a purchase, and in loyalty programs where a points-redemption endpoint doesn't check whether the same reward has already been claimed in a nearly simultaneous second request, a race condition that lets an attacker redeem the same limited stock twice by firing two requests close enough together that the first check-then-act sequence hasn't completed for either one yet.

OWASP's 2023 update added "unrestricted access to sensitive business flows" as its own category precisely because these issues don't show up in a conventional vulnerability scanner. A scanner checks for known bad patterns in code: missing input validation, outdated dependencies, insecure configurations. It has no concept of what a "sensible" rate of ticket purchases looks like for your specific business, or how many failed login-adjacent password reset attempts should trigger a hold on an account. That judgment has to come from someone who understands the business the API serves, working alongside the people who understand how to defend it.

This is where security stops being a purely technical discipline and starts requiring product and security teams to actually sit in the same room, because the vulnerability is only visible if you understand what the business is trying to protect.

I think this category is under-discussed relative to how much damage it causes, because it doesn't fit the narrative of "attacker exploits flaw." It fits a quieter and more uncomfortable narrative: the system worked as specified, and the specification didn't account for someone using it at a scale or in a sequence the business never anticipated.

The Request You Never Meant to Trust

Business logic abuse assumes the attacker is talking to your API directly. A closely related and increasingly common problem is your own API talking to something else on the attacker's behalf, without meaning to. Server-side request forgery earned its own line item in the 2023 OWASP update for exactly this reason, and it's a good example of a vulnerability class that becomes far more relevant as APIs increasingly call other APIs behind the scenes.

The pattern: an API accepts a URL as part of a request, maybe to fetch a user's avatar from a URL they provide, to validate a webhook endpoint, or to generate a preview of a link someone pasted into a chat message. The server, trusting that this is a reasonable thing to do, goes and fetches that URL itself. If there's no restriction on what URLs are acceptable, an attacker can point that "fetch this URL" parameter at internal infrastructure that isn't supposed to be reachable from the outside world: an internal admin panel, a cloud metadata endpoint that hands out temporary credentials, a database management interface sitting on a private network segment that was never meant to be exposed.

Cloud metadata endpoints deserve specific attention here, because SSRF against them has been behind some of the more consequential breaches of the last several years across the industry generally. Most major cloud providers expose an internal metadata service, reachable only from inside the virtual machine or container itself, that hands back temporary credentials for whatever role the compute instance is running as. If your API can be tricked into making a request to that internal address on the attacker's behalf, and the response is reflected back or used internally in a way the attacker can observe, the attacker effectively gets your cloud credentials without ever touching your cloud console.

The defensive posture here is narrower and more mechanical than most of the categories discussed so far: any API that fetches a URL provided by a client should validate that URL against an explicit allowlist of acceptable destinations, rather than trying to blocklist known-bad ones, because blocklists are trivially bypassed through redirects, alternate IP representations, and DNS tricks that resolve to internal addresses only after the initial validation check has already passed. Network-level segmentation matters too: the compute environment running your API generally shouldn't have unrestricted network access to your internal infrastructure just because it's convenient during development.

Rate Limiting Is Not a Nice-to-Have, It's a Load-Bearing Wall

I've watched more than one team treat rate limiting as a performance optimization, something you add later if the infrastructure bill gets too high, rather than a security control. That framing misses what rate limiting is actually defending against.

Unrestricted resource consumption sits at API4 in the current OWASP list, and it covers more than just denial-of-service concerns. An API with no meaningful limits on request volume, payload size, or resource-intensive operations per account is an API that treats "one legitimate user doing a reasonable thing" and "an automated script doing that same thing ten thousand times a second" identically. The API can't tell the difference, because nothing was built to make the distinction.

This connects directly back to the business logic problems described earlier. Credential stuffing, the practice of taking a breached list of username-password pairs from one service and testing them automatically against another, depends entirely on being able to make thousands of login attempts without meaningful friction. An API with proper rate limiting per account and per source, combined with progressive delays after failed attempts, turns a script that could test a million credential pairs in an hour into one that takes days, which changes the economics enough that many attackers move on to easier targets.

The same logic applies to data scraping through legitimate but unthrottled endpoints. An API that lets any authenticated user page through the entire user directory without any cap on requests per minute is an API that will eventually have its entire user base exported by someone who was never supposed to have bulk access to it, using nothing more sophisticated than a loop and a valid login of their own.

Rate limiting doesn't stop a determined, well-resourced attacker. It stops the overwhelming majority of automated abuse that depends on cheap, high-volume attempts, which is most real-world attack traffic.

Configuration Drift: The Quiet Failure Mode

Rate limiting is a control you have to deliberately build. Misconfiguration is different: it's usually a control you already have, set wrong, by default, without anyone deciding to set it that way. Security misconfiguration has been on every version of the OWASP list since the framework existed, and it remains there for a reason that has nothing to do with the difficulty of the underlying fix. Most misconfigurations are trivial to correct once identified. The problem is that nobody looks until something goes wrong.

Verbose error messages that return full stack traces, including internal file paths, database query structure, and sometimes even fragments of configuration, are still routinely found in production APIs, because the detailed error output that makes debugging fast during development was never switched off before shipping. An attacker doesn't need to exploit anything to benefit from this. They just need to send a malformed request and read what comes back.

Default credentials on administrative interfaces that were meant to be temporary during setup and never rotated. CORS policies configured with a wildcard origin because it made local development easier and nobody tightened it before deployment. Cloud storage buckets backing an API's file upload feature, configured as publicly readable because that was the fastest way to get image serving working, with no process to review that configuration before the feature reached real users.

None of these require any technical sophistication to exploit. They require someone noticing them, which is precisely why they're so persistent: misconfiguration isn't a skills gap, it's a review gap, and most engineering teams don't have a reliable process that catches a security-relevant setting before it reaches production.

The practical answer is less about individual vigilance and more about removing the opportunity for the mistake to reach production silently. Automated configuration scanning as part of the deployment pipeline, infrastructure defined as code and reviewed the same way application code is reviewed, and a deliberate policy that every new environment starts from a hardened baseline rather than the most permissive settings that got a proof of concept working fastest. The individual fixes are boring. The discipline to apply them consistently, across every environment, every time, is the actual hard part.

Trusting Someone Else's API Is Still Your Problem

The final category OWASP added in its 2023 revision, unsafe consumption of APIs, addresses something that's become unavoidable as modern applications are assembled from dozens of third-party services rather than built as monoliths: payment processors, mapping services, authentication providers, analytics platforms, communication APIs. Your application's security posture is no longer fully determined by code your team wrote.

The failure pattern here is subtle because it inverts the usual security instinct. Developers are trained to be suspicious of input coming from users. They are much less trained to be suspicious of input coming from a trusted, paid, well-documented third-party API, even though that data still needs to be validated before it's used, because the third party's API can be compromised, can have its own vulnerabilities, or can simply change its response format in a way your integration wasn't built to handle safely.

A webhook received from a payment provider, if not properly authenticated with a signature check, can be spoofed by anyone who figures out or guesses the webhook URL, potentially triggering "payment confirmed" logic without an actual payment occurring. Redirect URLs returned from a third-party OAuth provider need validation before your application blindly follows them, because a compromised or misconfigured third party can turn your own redirect handling into an open redirect that phishes your users while appearing to come from your domain.

This isn't a call to distrust every vendor integration. It's a reminder that the trust boundary in a modern application doesn't end at your own code. Every external API your system calls is a dependency you didn't write, can't fully audit, and are nonetheless accountable for when something goes wrong, in exactly the same way a vulnerable open-source library becomes your vulnerability the moment you import it.

What Happens Under Deadline Pressure

Step back from the individual categories for a moment, because listing them doesn't actually explain why they keep recurring at companies with genuinely competent engineering teams. Knowing what BOLA is doesn't prevent it. Something in how software actually gets shipped keeps producing the same handful of mistakes, year after year, across organizations that would all say, honestly, that they care about security.

The honest answer is that security requirements and delivery pressure are structurally in tension, and in most organizations, delivery pressure has a clearer owner, a clearer deadline, and a much louder voice in the room. A product manager can point to a launch date on a roadmap that other teams, marketing, sales, leadership, are already counting on. A security review that says "we need two more weeks to properly test authorization on every new endpoint" is asking the org to absorb a cost that's diffuse and probabilistic against a cost, the missed launch date, that's specific and certain.

Under that asymmetry, the rational individual decision at almost every point along the way is to ship, and defer the thorough authorization review to "a follow-up sprint" that competes for priority against the next feature the same pressure is already generating. Nobody in that sequence made a bad-faith decision. Each individual tradeoff, in isolation, looks reasonable. The aggregate result, across dozens of endpoints and multiple quarters, is a system with authorization gaps distributed unpredictably across the codebase, discovered eventually by whoever finds them first: a security researcher, an automated scanner, or an attacker.

Security rarely fails at the moment a vulnerability gets exploited. It fails earlier, at the moment someone reasonably decided that fixing it now would cost more than fixing it later, and later never quite arrives.

This is why I've become skeptical of security advice that's purely technical: use this library, follow this checklist, run this scanner. All of that is necessary and none of it is sufficient, because the actual failure point is organizational. Teams that consistently ship more secure APIs aren't teams with smarter developers. They're teams where security review has a real, non-negotiable gate in the deployment process, the same way a failing test suite blocks a merge, rather than a recommendation that can be quietly deprioritized when the calendar gets tight.

Versioning Is a Security Decision, Not Just a Compatibility One

Teams generally think about API versioning as a backward-compatibility problem: how do we change the API without breaking clients that haven't updated yet. That framing is correct as far as it goes, but it misses a security dimension that matters just as much, which is that every version of your API you keep alive is a version you're committing to defend, at full strength, for as long as it's reachable.

This matters more than it initially seems because security fixes don't always propagate cleanly across versions. A team discovers and fixes a BOLA vulnerability in v2 of an endpoint. If v1 of that same endpoint is still live, serving older mobile app installs that haven't updated, the fix applied to v2 does nothing for v1 unless someone deliberately backports it, which requires remembering that v1 still exists, still matters, and still needs the same scrutiny as the version everyone is actively working on. In practice, older versions get less attention precisely because engineering focus has moved to the current version, which means the oldest, least-maintained version of your API is often also the one carrying the oldest, least-fixed set of vulnerabilities, still fully reachable by anyone who knows the URL pattern.

This creates a genuine and uncomfortable tension with mobile app development specifically, because you can't force every user to update their app on your timeline. Some meaningful percentage of your user base is always running a version from six months or a year ago, on a device that may not even support the latest OS update, and that old app version is calling an old API version that may not have received the same security attention as the current one. Deprecating an API version cleanly, meaning actually turning it off rather than just discouraging its use, requires either forcing app updates through the app stores, which platforms support but which frustrates users, or maintaining parallel security posture across every live version indefinitely, which is expensive and easy to under-resource.

An API version doesn't become safe to ignore just because the engineering team has moved on to the next one. It becomes more dangerous, because attention moved and the surface didn't shrink.

The practical discipline here is treating API deprecation as an active, resourced process with a real deadline, not a passive hope that usage will taper off naturally. That means telemetry on which API versions are actually still receiving traffic, a genuine sunset date communicated to whatever teams or partners depend on the old version, and a hard cutoff enforced at that date rather than extended indefinitely because someone, somewhere, still hasn't updated. The alternative, keeping every version alive forever because turning one off might break something, guarantees that your API surface only ever grows, and that the oldest, least-scrutinized parts of it grow right alongside it.

The Developer Who Inherits Someone Else's API

There's a specific and common scenario worth examining on its own, because it's where a lot of real-world API vulnerabilities actually get introduced: not at initial build time, but during maintenance, by a developer who didn't design the system and is working from incomplete context.

A new engineer joins a team maintaining an API that's grown organically over three years. They're asked to add a new endpoint that's similar to an existing one, retrieve a resource by ID, in a slightly different context. The fastest, most obviously correct approach is to copy the existing endpoint's structure, because it's already been through code review once, it already works, and the pattern is right there in the codebase as an example to follow.

If the original endpoint had a subtle authorization gap, that gap gets copied forward into the new endpoint, now duplicated, and the new engineer had no reason to question a pattern that's already live in production and presumably already reviewed. This is how a single missed authorization check in an early version of an API can propagate across a dozen endpoints over several years, each one individually reviewed and approved, none of the reviewers catching the underlying pattern because each review was scoped to "does this new endpoint look like the ones next to it," and the ones next to it were the problem.

This is a genuinely difficult failure mode to design around, because it isn't caused by carelessness. It's caused by the entirely reasonable engineering instinct to follow established patterns rather than reinvent every endpoint from first principles. The mitigation isn't "review harder." It's building authorization as a shared, testable component that every endpoint calls into rather than something each endpoint re-implements by example, so that fixing the pattern once actually fixes every place it was used, instead of requiring someone to hunt down every copy.

GraphQL Changed the Shape of the Problem, Not the Problem

Most of what I've described so far applies naturally to REST APIs, where each endpoint corresponds roughly to a resource and a verb. GraphQL, now widely adopted specifically because it lets a client request exactly the fields it needs in a single query rather than making several separate REST calls, introduces the same underlying risks in a form that's genuinely harder to reason about, because the attack surface isn't a fixed list of endpoints anymore. It's every possible combination of fields, nested queries, and relationships the schema allows.

A REST API with fifty endpoints has, roughly speaking, fifty things to authorize correctly. A GraphQL API with a comparably sized schema might expose thousands of theoretically reachable query shapes, because clients can nest queries arbitrarily, following relationships between types as deep as the schema permits. If a User type has a friends field that returns more User objects, and each of those has its own friends field, a client can, in a single request, ask for a user's friends' friends' friends, recursively, unless something explicitly stops them. This isn't a contrived example. Deeply nested queries against under-restricted GraphQL schemas have been used to extract enormous amounts of relationship data in single requests, and to cause denial-of-service conditions by forcing the server to resolve an exponentially growing number of nested objects from one incoming query that looks, on its face, like a single legitimate request.

The authorization problem compounds here rather than simplifying, because the same BOLA concern that applies to a single REST endpoint now has to be enforced consistently across every possible path through the graph that reaches a given object type, not just the specific endpoint a developer remembers to protect. It's straightforward to add an ownership check to a getInvoice REST endpoint. It's considerably harder to guarantee that the same Invoice object, reachable through a user.invoices field, a company.invoices field, and a direct invoice(id:) query, gets the identical authorization check applied consistently across all three paths, especially when different engineers implemented each resolver at different times.

A GraphQL schema is not a smaller attack surface because it looks like a single endpoint. It's often a larger one, because the client, not the server, decides the shape of the request.

The practical response isn't to avoid GraphQL, which offers real and legitimate benefits for client efficiency. It's to enforce query depth limits and query complexity scoring at the gateway level before a query is ever executed, so that an unusually deep or expensive query is rejected before it reaches the resolvers, and to make sure authorization logic lives at the data-fetching layer, applied consistently to every resolver that can return a given type, rather than being scattered across individual query definitions where it's easy for one path to be protected while a structurally identical path is overlooked.

What Actually Shows Up in an API Penetration Test

It's worth being concrete about what a competent API security assessment actually looks like in practice, because the term gets used loosely and the reality is more specific than "we ran a scanner against it."

A serious API assessment starts with authenticated access as at least two distinct user roles, ideally more, because the majority of the interesting findings only appear when you compare what one authenticated user can access against what a different authenticated user, with different permissions, can also reach if they simply substitute their own valid token into a request meant for someone else's resource. This is where BOLA and broken function-level authorization actually get found: not by scanning for a known signature, but by systematically trying "my valid credentials, someone else's object ID" across every endpoint that accepts an identifier.

It involves examining the full request and response for every endpoint the client makes, not just the ones the tester expects to be interesting, because APIs frequently return more data in a response than the client interface actually displays, a pattern OWASP specifically calls out as broken object property level authorization. An endpoint might correctly restrict which invoice you can view by ID, and still leak the requesting company's internal margin data in a field the response includes but the app's UI simply never renders. The data left the server. The fact that the app chose not to display it is not a security control.

It involves deliberately sending malformed, oversized, and logically inconsistent requests, not to crash anything destructively, but to see how the API responds when it receives input that doesn't match what a well-behaved client would ever send, because the well-behaved client isn't the one you're defending against.

And it involves reviewing the API's documentation, if any exists, against what the API actually accepts, because a meaningful number of real-world vulnerabilities live specifically in the gap between documented, expected behavior and undocumented parameters or endpoints that still work but were never meant to be exposed, often left over from an earlier version of the API that technically still functions.

None of this requires exotic tooling. It requires methodical, patient testing that assumes the attacker has a valid account of their own, which is a realistic assumption for most APIs, because creating an account is usually free and instant.

The API Gateway Is Doing Less Than You Think It Is

A lot of organizations have a quiet, comforting assumption sitting underneath their API security posture: we have an API gateway in front of everything, so the important controls are handled centrally. This is true for a narrower set of concerns than most teams realize, and the gap between what a gateway actually does and what people assume it does is worth being explicit about.

An API gateway is genuinely good at certain things. Terminating TLS in one place rather than in every service. Enforcing coarse rate limits per API key or per source IP. Providing a single point for API key validation, so that individual services don't each need to implement key checking separately. Centralizing request logging in a consistent format, which helps enormously with the monitoring gap described elsewhere in this piece. Blocking traffic that doesn't match the expected schema at the perimeter, before it reaches application code at all. These are real, valuable, and worth having.

What a gateway generally cannot do, no matter how well configured, is object-level authorization, because that requires business context the gateway doesn't have. A gateway can confirm that a request carries a valid token. It has no way to know, without deep and often impractical integration with your application's data model, whether the specific invoice ID in this specific request actually belongs to the specific user that token represents. That check has to happen inside the application, against the actual data, because it's the only layer that has the context to answer the question correctly.

I mention this because I've seen the assumption "we have a gateway" used, implicitly, as a reason not to prioritize authorization work at the application layer, on the theory that the gateway is already handling security. It's handling a real and useful slice of security. It is not handling the slice responsible for the majority of real-world API breaches. Conflating gateway-level controls with application-level authorization is one of the more consequential misunderstandings I encounter in architecture reviews, precisely because it sounds reasonable and isn't obviously wrong until you trace through what the gateway can actually see about a given request.

Logging, Monitoring, and the Six-Week Gap

Go back to the T-Mobile example for a moment, because one detail matters more than the headline number. The attacker had access to the API for approximately six weeks before it was noticed, from late November 2022 until detection on January 5, 2023. That gap is the part of the story that should concern engineering teams more than the vulnerability itself, because it says something about detection capability, not just prevention.

A vulnerability that gets exploited once and caught within minutes is a bad day. A vulnerability that gets exploited continuously for six weeks without triggering any alert is a much deeper problem, because it means the API had no meaningful behavioral monitoring capable of distinguishing "one account querying a lot of records very quickly, repeatedly, at a volume no real user session generates" from normal traffic.

This is where API security connects directly to observability, a discipline that's often owned by a completely different team with completely different priorities. Application logs built primarily for debugging tend to capture what a developer needs to diagnose an error: request path, response code, maybe a stack trace on failure. They rarely capture what a security analyst needs to spot abuse: which specific object IDs were requested, by which account, at what rate, compared against that account's historical baseline.

Building that second kind of visibility isn't free, and it isn't automatic. It requires deciding, deliberately, that API access patterns are a security-relevant signal worth capturing and monitoring, not just an operational one worth capturing for uptime dashboards. Anomaly detection on API traffic, flagging accounts that suddenly query at a rate or a breadth wildly outside their own established pattern, is one of the more effective practical controls available, precisely because it doesn't require predicting the specific vulnerability an attacker will use. It just requires noticing that something is happening at a scale no legitimate user session produces.

An API without behavioral monitoring isn't secure. It's just quiet, right up until someone tells you otherwise, usually a journalist or a regulator, weeks after the fact.

Your API's Security Depends on Packages You Never Reviewed

There's a supply chain dimension to API security that runs parallel to the well-known problem of vulnerable open-source dependencies in application code generally, but shows up in a specific and often overlooked way at the API layer: the frameworks and middleware that actually implement authentication, request parsing, and routing are themselves dependencies, and a vulnerability in one of them can undermine every security control your team carefully built on top of it.

An authentication middleware library with a subtle flaw in how it validates a JWT signature, for instance accepting a token signed with a different algorithm than the one the server expects, a class of vulnerability that has appeared in multiple JWT libraries across different languages over the years, can silently defeat authorization logic that is, on its own, perfectly correct. Every ownership check your team wrote, every scoped token, every careful piece of authorization logic downstream, assumes that the authentication layer beneath it is trustworthy. If that assumption is wrong, none of the layers built on top of it matter, because the attacker never needed to get past them. They got past the thing everything else was relying on.

This is why dependency management for API-critical libraries, specifically the ones handling authentication, session management, and request parsing, deserves a higher bar than general dependency hygiene applied uniformly across a codebase. Not every outdated dependency in a project is equally dangerous. A stale version of a formatting utility library is a minor risk. A stale version of the library validating every incoming token is a risk that sits directly underneath every other security control the API has.

Practically, this argues for treating authentication and authorization libraries as a distinct, higher-priority category in dependency scanning and patching, rather than letting them sit in the same queue as every other package update, competing for attention against dozens of lower-stakes upgrades. It also argues for genuinely understanding what a security-critical dependency does, at least at a conceptual level, rather than treating it as an opaque black box that "handles auth," because the ability to recognize when an update to that library actually matters, versus when it's a routine version bump, depends on understanding roughly what it's protecting and how.

Zero Trust Isn't a Buzzword Here, It's the Actual Architecture

"Zero trust" gets used loosely enough in marketing material that it's worth being specific about what it actually means at the API layer, because stripped of the branding, it's a genuinely useful and concrete principle: no request should be trusted by virtue of where it came from. Not because it originated inside your own network. Not because it came from a service you built. Not because the caller authenticated successfully five minutes ago.

NIST's zero trust guidance, along with related microservices security guidance, formalizes what security-conscious API architectures have been converging on for years: every request, from every source, internal or external, gets evaluated on its own merits, every time. An internal microservice calling another internal microservice still authenticates. Still gets its authorization checked against the specific resource it's requesting. Still gets logged. The fact that both services live inside the same private network is not treated as a substitute for that verification, because a compromised service inside your network is a more dangerous attacker than one outside it, precisely because it's already past the perimeter controls everyone else is relying on.

This matters more with every passing year because the traditional network perimeter, the idea that "inside the firewall" meant "trusted," has been eroding steadily as architectures move toward microservices, containers, and multi-cloud deployments where there often isn't a single coherent perimeter left to defend. The API call between two services inside your own infrastructure needs the same rigor as the API call from an external partner, because from a security standpoint, the distinction between them is architectural convenience, not an actual guarantee about who or what is making the request.

The Part of the Job Nobody Puts on the Roadmap

I want to end on something less technical, because the technical controls, proper object-level checks, rate limiting, scoped tokens, inventory management, are all well documented, genuinely learnable, and not the actual bottleneck for most organizations. The bottleneck is that API security work is largely invisible when it's done well.

A properly authorized endpoint doesn't generate a headline. A rate limit that quietly stopped a credential stuffing attempt at 2 a.m. doesn't show up in a sprint retrospective as a win, because nobody outside the security team ever saw the attempt happen. The absence of a breach isn't a deliverable that fits neatly into a roadmap slide next to the features that shipped this quarter, and in an industry that measures engineering output largely by what got built and released, work whose entire purpose is to prevent something from ever becoming visible is structurally undervalued, no matter how many times leadership says security matters in an all-hands meeting.

The best API security work in your organization right now is probably being done by someone whose name will never come up unless they're wrong.

That's not a reason for cynicism. It's a reason to be deliberate about how security work gets recognized and resourced, because "we'll get to it" is not a policy, it's a default, and defaults compound. Every API you ship today is a commitment your organization is making to defend it indefinitely, against threats and attack patterns that don't exist yet, using a team whose attention will always be pulled toward whatever ships next. The organizations that handle this well aren't the ones with the most sophisticated tooling. They're the ones that treat authorization, inventory, and monitoring as first-class engineering work with the same non-negotiable status as functional correctness, rather than a compliance checkbox addressed once before launch and revisited only after something has already gone wrong.

The API layer is not going to become less central to how software gets built. If anything, the direction is the opposite: more of what we build is composed from APIs, calling other APIs, on behalf of clients that are themselves just another API consumer. The attack surface this creates isn't a phase we're passing through. It's the architecture now, and it will remain the architecture for the foreseeable future.

The question worth sitting with isn't whether your APIs have vulnerabilities. Every non-trivial API has some. The question is whether your organization would notice in six weeks, or in six minutes, and whether that answer is a matter of deliberate design or simply a matter of luck that hasn't run out yet.

What's the actual gap in your organization: is it that engineers don't know how to build authorization correctly, or that the process never gives them the time to do it before the deadline arrives?
